# تشخيص حي: المصادقة والإشعارات وبيانات لوحة المجلس

**التاريخ:** 2026-09-07
**النطاق:** فحص موجّه على الهاتف المتصل فقط، مع إصلاح موضعي لتفاعل لوحة المجلس.
**القيود الملتزم بها:** لا نشر، لا migration، لا كتابة بيانات إنتاج، لا تعطيل أو تغيير App Check أو Firestore Rules، ولا commit أو push.

## الوضع الحالي

- الجهاز المتصل: Xiaomi/Redmi `23073RPBFG`، Android 15 (SDK 35).
- الحزمة العاملة: `com.alrahmat.village_council`، نسخة Debug.
- صلاحية Android للإشعارات `POST_NOTIFICATIONS` ممنوحة.
- تم الاحتفاظ بحالة التطبيق وبيانات تسجيل الدخول؛ لم يحدث uninstall أو clear-data أو logout.

## السبب الجذري المثبت

سجل الهاتف يثبت أن App Check لا يمنح التطبيق رمزًا صالحًا:

- `Error returned from API. code: 403 body: App attestation failed.`
- ثم `Error getting App Check token. Error: ... Too many attempts.`

لذلك تتلقى Cloud Functions الطلبات كـ `unauthenticated`، وليس لأن جلسة Firebase Auth للمستخدم انتهت. ظهرت النتيجة نفسها في:

- `getCouncilDashboardMetrics`.
- `getBookingAvailability`.
- `getPayableCharges`.

وهذا يفسر عمليًا اختفاء/فشل مؤشرات الحجز والرسوم والإيصالات، ورسالة «انتهت جلسة الدخول» التي يحولها العميل من رمز `unauthenticated`.

كما ظهرت استعلامات Firestore مرفوضة (`PERMISSION_DENIED`) لبيانات مالية وسجل تدقيق. لا يصح توسيع Rules لعلاجها قبل فصل كل استعلام بحسب عضوية الحساب ودوره؛ لم تُعدّل القواعد في هذه المهمة.

## الإشعارات وFCM

- سلسلة التطبيق موجودة: حفظ رمز FCM عند تغير حساب Firebase Auth، إزالة الرمز عند logout، ومعالجة `onTokenRefresh`؛ ولا تسجل الرموز نفسها في السجل.
- دالة الخلفية المحلية `onNotificationCreated` تقرأ رموز المستخدم وتزيل غير الصالح منها عند رد FCM.
- لم يظهر في السجل دليل على رفض FCM نفسه أو على فقدان صلاحية Android للإشعارات.
- لا يمكن اعتماد اختبار وصول إشعار حقيقي بين حسابين بينما App Check يفشل وتُحجب العمليات التي تنشئ البيانات/الإشعارات. لم تُفترض مشكلة token ولم يُعدّل تدفق FCM بلا دليل.

## إصلاحات منفذة محليًا

في `lib/presentation/screens/council/council_dashboard_screen.dart`:

1. أصبحت تنبيهات لوحة المجلس المهمة قابلة للنقر وتفتح فقط شاشة المراجعة المصرح بها:
   - الحجوزات المعلقة → طلبات الحجز.
   - الإيصالات المعلقة → مراجعة المدفوعات.
   - الاشتراكات المتأخرة → الإدارة المالية.
2. أصبحت عناصر «آخر النشاطات» قابلة للنقر، وتستعمل `NotificationDeepLink` نفسه المستخدم في مركز الإشعارات؛ تُعلَّم كمقروءة أولًا ثم تفتح الوجهة الخاصة بالمجلس المرتبط.
3. لم تُمنح أي قدرة جديدة: تظهر الوجهات المالية/الإدارية فقط إذا كانت القدرة الحالية تسمح بها.

## ما لم يُعدّل عمدًا

- لم يُغيّر App Check أو طريقة التحقق منه. هذا حاجز إعداد بيئي/إصدار يجب معالجته بشكل منفصل وبموافقة صريحة بعد التحقق من إعداد Android/Play Integrity في Firebase Console.
- لم تُغيّر Firestore Rules أو Cloud Functions أو بيانات Production.
- لم يتغير نموذج «عضو + دور مالي»؛ فصل العضوية الأساسية عن الدور المالي محفوظ كما هو.

## المخاطر والخطوة التالية

الخطر الحالي ليس من واجهة لوحة المجلس، بل من فشل attestation الذي يجعل خدمات الإنتاج المحمية غير متاحة على هذا الهاتف. الخطوة التالية الآمنة هي مراجعة إعداد App Check لهذا التطبيق/توقيع Android في Firebase Console وPlay Integrity دون تخفيف الحماية، ثم إعادة اختبار الجهاز وحسابين حقيقيين لحدث حجز واحد وإشعار واحد.
